# 协作纪律

这些规则不是建议，是这一轮反复确认过的边界。违反其中任意一条，都会造成返工或信任损失。

## 一、问 ≠ 做

- 用户问"为什么/什么区别/能不能/怎么做"，**只回答、只分析**。
- 只有明确的"做 / 继续 / ok / 开始"才是开工口令。
- 不确定时先问一句"要我做吗"，不要用"顺便改一下"当作许可。
- 已经动了但用户没让动的改动，**立即回退**，回退也用编辑工具逐块还原（不要 `git checkout` 批量覆盖用户其他改动）。

## 二、不碰用户的桌面与正在使用的应用

- 不打开、不激活、不关闭用户正在用的应用。
- 不移动鼠标、不代按键盘（除用户明确授权的测试）。
- 自测时用独立的测试实例 / 探针，不用真实交付去打扰用户当前工作。
- 需要用户操作的（授权、说话、点击），明确告诉用户做什么，自己不代做。

## 三、不用命令行改代码与文档

- 只用 `edit` / `write` 工具修改文件。
- 禁止 `sed -i`、`cp` 覆盖源码、`python -c` 批量替换——哪怕只是改一个字段名、改一行注释。
- 命令行的合法用途：只读查询（`grep`/`git log`/`git diff`）、构建、测试、打包、签名、发布、安装。
- 机械替换也属于改代码，没有例外。

## 四、一处实现

- 同一个判断只允许一份实现；新增能力先复用现有函数。
- 配置只在消费端使用：探测函数不接收配置，由消费方决定行为。
- 删除死代码：不再使用的函数、分支、注释一并清理。

## 五、验证与汇报

- 先自己验证，再汇报；汇报给证据（数字、日志行、文件路径、截图）。
- 不凭感觉说"好了"；不把"编译通过"当成"行为正确"。
- 未做的事单独列出（"我没有做 X，等你决定"），不要混在已完成里。
- 失败就停下说明原因，不掩盖、不绕过。

## 六、语言与文档

- 对话与文档用中文。
- 文档遵守简明语言规范：读者不需要猜；不用内部黑话；结论先行；一条一个信息点。
- 行为变更必须同步 `docs/SPEC.md`；架构或流程变更同步 `handover/`。
- commit message 用固定结构：标题 / 问题 / 发现过程 / 实现方案 / 实现过程 / 总结。

## 七、Git 与发布边界

- 不擅自 push、打 tag、创建 Release；等"发布/继续"指令。
- 不删除已发布的 tag/Release；不 force push；不改写历史（除非用户明确要求）。
- 发布前必须完成 `04-verification.md` 的门禁。
